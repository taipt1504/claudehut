#### Wave 0 — results (measured on this branch)

**W0-A — DONE (decision item; the decision is made).** The plan says bump `evals/conformance.sh:78`
"once, in whichever commit lands first". Taken literally that leaves the suite **red for every commit
between the bump and the last rule file**, because `[ "$RT" = "55" ]` is an equality — and a persistently
red suite destroys the revert-and-confirm-red signal every other wave-2 change depends on. **Resolution:
bump `+1` in the same commit as each rule file** (rows 14, 15, 16). Always green, minimal, and it cannot
happen earlier because there is no rule file to count yet. A manifest was considered and rejected as more
machinery than the problem needs. With the ambiguity defaults chosen (row 41 keeps the file count, row 16
drops the optional `r2dbc-locking.md`, row 51 takes the keep-the-filename branch) the final value is **58**.

**W0-B — DONE. Closed with a captured payload, commit `5cb64d2`.** Method: a disposable repo in the
scratchpad was wired to these hooks via `.claude/settings.json` and driven with `claude -p`, so a real
runtime delivered real payloads. No plugin install, no change to any real repo.

Real `PostToolUseFailure` payload (verbatim keys):
`session_id transcript_path cwd prompt_id permission_mode effort hook_event_name tool_name tool_input
tool_use_id error is_interrupt duration_ms`

```
error: "Exit code 1\nls: /no/such/dir/xyz: No such file or directory"
is_interrupt: false
duration_ms: 47
```

**There is no `tool_error` object and no `tool_response` on this event.** So the old paths
`.tool_error.{exit_code,type,stderr}` could never match — the 682/682 empty records were not a wrong
field name, they were a field that does not exist. `exit` is now parsed from the `Exit code N` first
line, `stderr` is the remainder, and `is_interrupt` types an interrupt separately from a real failure.
The plan's proposed `.error` / `.is_interrupt` was **right**; my earlier "also unsourced" note was
accurate about the docs but wrong about the outcome.

Also captured: a **successful** Bash fires `PostToolUse` with a full
`tool_response {stdout, stderr, interrupted, isImage, noOutputExpected}`; a **failing** one fires
`PostToolUseFailure` with no response object at all. Two events, two shapes.

**Row 6 is unblocked.** The `schema_keys` drift detector stays in place — it is what would catch the
next such change without needing a probe.

**W0-C — DONE, both halves. Row 18 is `confirmed`, and it is BIGGER than "add `|fork`".**
`code.claude.com/docs/en/cli-reference`, verbatim: *"`--fork-session` | When resuming, create a **new
session ID** instead of reusing the original."* And `code.claude.com/docs/en/hooks` enumerates the
SessionStart matcher values verbatim as *"`startup`, `resume`, `clear`, `compact`, `fork`"* — **`fork` is
a documented source**. `hooks/hooks.json:5` matches `"startup|resume|clear|compact"`. Therefore a forked
session gets a brand-new `session_id`, its SessionStart hook **never fires**, `bootstrap.sh` never runs,
and no state, digest or learnings are armed — the plugin is **inert in every forked session**.

**Verified empirically** (commit `9846f46`): driving `bootstrap.sh` with `{"session_id":"FORK-2",
"source":"fork"}` after a `PARENT-1` startup produced a fresh `FORK-2.json` at `phase=discover`,
`reuse_scan=false`, with `PARENT-1.json` left orphaned. The script is source-agnostic — the harness
matcher is the only thing stopping it today.

> **Trap recorded for row 18: do NOT ship the matcher fix alone.** Adding `|fork` without fork-awareness
> makes `bootstrap.sh:39-41` arm the new sid at `set-phase discover`, resetting a fork taken mid-implement
> back to the first phase. The matcher change and the fork-aware bootstrap must land in the same commit.

**Row 18 IS sized now — and the answer is that inheritance is impossible.** Captured from a real
`claude --resume <sid> --fork-session`:

```
sid fd3ee5e8  source=startup  keys: session_id, transcript_path, cwd, hook_event_name, source
sid b2e6ddd4  source=fork     keys: session_id, transcript_path, cwd, hook_event_name, source
```

The fork gets a new session id, `source:"fork"` is delivered, and the key set is **identical** — no
`parent_session_id`, no `forked_from`, nothing. The fork's transcript was also checked: the parent sid
appears **zero** times in it, and the only `sessionId` inside is the fork's own. There is no payload
path and no transcript path to the parent.

So row 18 is a **policy decision**, not a copy-forward. The three options are the complete set:
- **(a) arm at discover** — current behaviour once the matcher is fixed; resets a mid-implement fork.
- **(b) do not arm on fork** — the write gate then fails open and the workflow becomes optional, which
  is exactly what the `opt #1` rationale at `bootstrap.sh:25-29` exists to prevent.
- **(c) adopt the newest state file in the project** — races with concurrent sessions and can silently
  attach a fork to an unrelated task.

Note the real SessionStart payload is **leaner than the documented common fields** — no `prompt_id`,
no `permission_mode`, no `model`. Any future hook work should assume these five keys only.
