## Measurements taken for this batch

Two `[unverified]` items in the plan gate real edits. Both were measured before the edits that depend
on them, on Claude Code **2.1.234**.

### M1 — `plugin_errors` does not exist in the `system/init` event

`scripts/load-probe.sh:31` reads `.plugin_errors // []` and `:36` gates on the result being `[]`.
The complete key set of a real `system/init` event, captured with
`claude -p --plugin-dir . --output-format stream-json --verbose`:

```
agents  analytics_disabled  apiKeySource  capabilities  claude_code_version  cwd
fast_mode_disabled_reason  fast_mode_state  mcp_servers  messaging_socket_path  model
output_style  permissionMode  plugins  product_feedback_disabled  session_id  skills
slash_commands  subtype  terminal_slash_commands  tools  type  uuid
```

There is no `plugin_errors` key. W22 is confirmed: the `//` default converts "field missing" into
"field says everything is fine", and the probe reduces to `loaded >= 1` while printing
"PASS - plugin loads cleanly".

**This changes W22's fix.** The plan proposes asserting key presence and failing loudly if it is
absent — which on this runtime would fail 100% of the time, on the very release-checklist step W17
newly adds. The plan anticipated this branch and said to find out first. What the event *does* carry
is a complete component roster, and that is a stronger signal than the absent key ever was:

```json
{"name":"claudehut","path":"…","source":"claudehut@inline","version":"0.11.0"}
agents: 14 claudehut entries    skills: 10 claudehut entries
```

which matches the tree exactly (`ls agents/*.md` → 14, `ls -d skills/*/` → 10). A roster assertion
catches the P6 over-declare class the probe exists for — an over-declare drops components from the
roster — where the `plugin_errors` gate never could.

### M2 — the subagent hook payloads, captured end to end

Probed with a project-scoped `SubagentStart`/`SubagentStop` hook pair in a throwaway repo, dumping
raw stdin. Complete key sets:

| Event | Keys |
|---|---|
| `SubagentStart` | `agent_id` `agent_type` `cwd` `hook_event_name` `prompt_id` `session_id` `transcript_path` |
| `SubagentStop` | the above **plus** `agent_transcript_path` `background_tasks` `effort` `last_assistant_message` `permission_mode` `session_crons` `stop_hook_active` |

Four consequences for F5:

1. **`effort` is absent on `SubagentStart`.** The plan flagged this `[unverified]`; it is now measured.
   `record-dispatch.sh` must not write it — that is precisely the defect class that produced 682
   hollow `PostToolUseFailure` records in v0.11.
2. **`effort` is present on `SubagentStop`**, as an object: `.effort.level` (observed `"xhigh"`).
3. **`agent_id` is present on both events** — the correct join key for pairing a start with its stop
   and deriving wall duration.
4. **`agent_transcript_path` is present on `SubagentStop`.** This hands us the per-agent transcript
   directly, and dissolves the undocumented `{project}` path-mangling problem that §5/F1 named as a
   blocker on ever deriving p95 turns.

### M3 — the authoritative load check has never once produced a verdict

Found by doing what W17 asks for: running the probe. The shipped `scripts/load-probe.sh` invokes

```
claude -p "…" --plugin-dir "$ROOT" --output-format stream-json
```

and the CLI rejects that combination outright:

```
Error: When using --print, --output-format=stream-json requires --verbose
```

So the probe captures no stream, finds no `system/init` event, and exits 1 with
*"FAIL - no system/init event in stream (probe could not start)"* — **on a perfectly healthy plugin,
every time it has ever been run.** `.github/workflows/ci.yml:6-7,:101-104` calls this file *"the
authoritative load check"* twice.

That makes three independent layers of nothing on the same file: it is on no checklist (W17), its gate
is vacuous (W22), and it cannot execute (M3). This is the same shape as v0.11's central finding — a
mechanism that is configured, green, and does nothing — and it is the strongest possible argument for
W17, because putting the probe on the checklist is what surfaced it.

**Revert-to-red for the new probe, done against an isolated copy of the tree** (never the shared
checkout): declaring `"agents": ["./agents/claudehut-reviewer.md"]` in `plugin.json` — the P6
over-declare class, where declaring the field replaces the default scan — drops 13 of 14 agents. The new
probe fails and names all thirteen. The old probe, run against that same sabotaged tree, prints its
usual "probe could not start".

**One limitation, measured and recorded so nobody banks it.** MF-12's landmine (a `skills` subset on a
marketplace entry whose `source` is `"./"` silently drops every unlisted skill) could **not** be
reproduced through this probe: `--plugin-dir` loads the plugin inline and never consults the marketplace
entry, so all 10 skills still registered with the subset declared. MF-12 remains doc-sourced, and the
conformance assertion for it is the right instrument — the load probe cannot cover marketplace-entry
semantics at all.
