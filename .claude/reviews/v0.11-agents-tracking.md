### M1 — `plugin_errors` does not exist in the `system/init` event

`scripts/load-probe.sh:31` reads `.plugin_errors // []` and `:36` gates on the result being `[]`.
The complete key set of a real `system/init` event, captured with
`claude -p --plugin-dir . --output-format stream-json --verbose`:

```
agents  analytics_disabled  apiKeySource  capabilities  claude_code_version  cwd
fast_mode_disabled_reason  fast_mode_state  mcp_servers  messaging_socket_path  model
output_style  permissionMode  plugins  product_feedback_disabled  session_id  skills
slash_commands  subtype  terminal_slash_commands  tools  type  uuid
```

There is no `plugin_errors` key. W22 is confirmed: the `//` default converts "field missing" into
"field says everything is fine", and the probe reduces to `loaded >= 1` while printing
"PASS - plugin loads cleanly".

**This changes W22's fix.** The plan proposes asserting key presence and failing loudly if it is
absent — which on this runtime would fail 100% of the time, on the very release-checklist step W17
newly adds. The plan anticipated this branch and said to find out first. What the event *does* carry
is a complete component roster, and that is a stronger signal than the absent key ever was:

```json
{"name":"claudehut","path":"…","source":"claudehut@inline","version":"0.11.0"}
agents: 14 claudehut entries    skills: 10 claudehut entries
```

which matches the tree exactly (`ls agents/*.md` → 14, `ls -d skills/*/` → 10). A roster assertion
catches the P6 over-declare class the probe exists for — an over-declare drops components from the
roster — where the `plugin_errors` gate never could.

### M2 — the subagent hook payloads, captured end to end

Probed with a project-scoped `SubagentStart`/`SubagentStop` hook pair in a throwaway repo, dumping
raw stdin. Complete key sets:

| Event | Keys |
|---|---|
| `SubagentStart` | `agent_id` `agent_type` `cwd` `hook_event_name` `prompt_id` `session_id` `transcript_path` |
| `SubagentStop` | the above **plus** `agent_transcript_path` `background_tasks` `effort` `last_assistant_message` `permission_mode` `session_crons` `stop_hook_active` |

Four consequences for F5:

1. **`effort` is absent on `SubagentStart`.** The plan flagged this `[unverified]`; it is now measured.
   `record-dispatch.sh` must not write it — that is precisely the defect class that produced 682
   hollow `PostToolUseFailure` records in v0.11.
2. **`effort` is present on `SubagentStop`**, as an object: `.effort.level` (observed `"xhigh"`).
3. **`agent_id` is present on both events** — the correct join key for pairing a start with its stop
   and deriving wall duration.
4. **`agent_transcript_path` is present on `SubagentStop`.** This hands us the per-agent transcript
   directly, and dissolves the undocumented `{project}` path-mangling problem that §5/F1 named as a
   blocker on ever deriving p95 turns.

### M3 — the authoritative load check has never once produced a verdict

Found by doing what W17 asks for: running the probe. The shipped `scripts/load-probe.sh` invokes

```
claude -p "…" --plugin-dir "$ROOT" --output-format stream-json
```

and the CLI rejects that combination outright:

```
Error: When using --print, --output-format=stream-json requires --verbose
```

So the probe captures no stream, finds no `system/init` event, and exits 1 with
*"FAIL - no system/init event in stream (probe could not start)"* — **on a perfectly healthy plugin,
every time it has ever been run.** `.github/workflows/ci.yml:6-7,:101-104` calls this file *"the
authoritative load check"* twice.

That makes three independent layers of nothing on the same file: it is on no checklist (W17), its gate
is vacuous (W22), and it cannot execute (M3). This is the same shape as v0.11's central finding — a
mechanism that is configured, green, and does nothing — and it is the strongest possible argument for
W17, because putting the probe on the checklist is what surfaced it.

**Revert-to-red for the new probe, done against an isolated copy of the tree** (never the shared
checkout): declaring `"agents": ["./agents/claudehut-reviewer.md"]` in `plugin.json` — the P6
over-declare class, where declaring the field replaces the default scan — drops 13 of 14 agents. The new
probe fails and names all thirteen. The old probe, run against that same sabotaged tree, prints its
usual "probe could not start".

**One limitation, measured and recorded so nobody banks it.** MF-12's landmine (a `skills` subset on a
marketplace entry whose `source` is `"./"` silently drops every unlisted skill) could **not** be
reproduced through this probe: `--plugin-dir` loads the plugin inline and never consults the marketplace
entry, so all 10 skills still registered with the subset declared. MF-12 remains doc-sourced, and the
conformance assertion for it is the right instrument — the load probe cannot cover marketplace-entry
semantics at all.

### M4 — `PreCompact` does carry `.session_id`

Measured on a real `/compact` of a resumed `-p` session. Complete key set:

```
custom_instructions  cwd  hook_event_name  prompt_id  session_id  transcript_path  trigger
```

`.session_id` is present and matches the session; `trigger` was `"manual"`. So `persist-state.sh`'s
long-standing assumption is **correct**, and the plan's §7 bullet *"Whether `PreCompact` carries
`.session_id` — assumed by `persist-state.sh:13`, never captured"* can be struck. `PreCompact` carries
no `agent_*` keys, and `custom_instructions` is an empty string on a manual compact.

This is the fourth hooked event whose payload is now measured rather than assumed, and the first one
where the assumption turned out to be right.

### M5 — `SubagentStop` fires without a matching `SubagentStart`

Unplanned, found while verifying F5 end to end. One real session produced **three** ledger records, not
two: the `Explore` dispatch's matched start+stop pair (same `agent_id`, 23 s apart), plus a third record
— a **stop with no start**, emitted during the compaction, carrying a fresh `agent_id`, an **empty**
`agent_type`, and an `agent_transcript_path` pointing at a file that was never written. The session's
`subagents/` directory held only the `Explore` transcript, and that run's stream shows no Agent tool call
at all.

Three consequences, all of which change how the ledger may be read:

1. **"One start + one stop per dispatch" holds for real Agent-tool dispatches, not for the ledger as a
   whole.** Any duration or count consumer must **join on `agent_id` and discard unmatched stops** —
   never count records. F6 must be written this way from the start.
2. **`agent_transcript_path` can dangle.** F1's plan to derive p95 turns by reading those transcripts has
   to tolerate a missing file. (The `{project}` path-mangling worry the plan raised is moot — the path is
   handed over verbatim — but a *different* failure mode replaces it.)
3. `verify-subagent.sh` is unaffected: its `case` sees `agent_type` `""` and falls through to the
   text-returning `*)` branch, so no false block. The orphan record is **not** suppressed — a hook records
   what the runtime hands it, and silently dropping records is how a ledger starts lying — but it is
   documented at the write site so no consumer assumes pairing.

## Deviations from the plan, and what they leave open

Three rows did not land as the plan wrote them. Each was a deliberate call with a stated reason, and
each is recorded here rather than rounded up to "done".

**A4-01 — PARTIAL, and correctly so.** The plan says to delete the restated coverage-table section from
all six auditor bodies. In every one of the six, `Read-only; do not edit.` was the **last line of that
section**. A wholesale delete would have stripped the read-only contract from six agents and then
re-added it to only the four that SAFETY-01 touches. So each Output section was rewritten rather than
deleted: the agent-specific evidence-scoping line, plus the read-only sentence, plus the git-state
clause where applicable. On `claudehut-reviewer` the trim is partial on purpose — its rendered example
table is the corpus's only concrete rendering of the coverage format and is genuinely not in
`review-rigor.md`; only the duplicated verdict/evidence prose came out. **This is a case where
following the plan literally would have deleted a safety contract**, which is exactly the class of
instruction that should be questioned rather than executed.

**A4-03 — NOT DONE, and the investigation is the deliverable.** The plan told us to verify first
whether the central MCP-degradation statement actually reaches an auditor. It does not, and the answer
is worse than the plan guessed on two counts: `skills/review/SKILL.md:103` sits **outside** the
"Every code-review dispatch prompt MUST carry" bullet list, **and** it contains no *"never hard-fail"*
wording in any form — it reads "degrade gracefully … review statically and say so". So the body prose
in `db-reviewer`, `perf-reviewer` and `security-auditor` is the **only** never-hard-fail instruction an
auditor ever sees, and the plan's proposed deletion would have hard-failed every project without an MCP
server. All three MCP sections were left fully intact, not even partially trimmed: the bytes are
bucket 4 — zero main-context saving — against real risk to a load-bearing instruction.

> **Open work.** A4-03 is reattemptable only after `skills/review/SKILL.md` grows a never-hard-fail
> clause inside its MUST-carry list. That is a skill change, not an agent change. Until then the
> duplication is the safe state and should not be "cleaned up".

**The plan's A1-02 baseline count was wrong.** It states `grep -n 'loops ≤\|cap 2\|reruns = 0'` returns
4 today. It returns **5 matches across 4 files** — `claudehut-brainstormer.md` carries two matching
lines. After the fix: 12 matches across 11 files. Both units are recorded so the next reader does not
"correct" one into the other.
