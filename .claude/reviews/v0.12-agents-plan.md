## 0. Cost axes for agents

| Axis | What it is | Where it is paid |
|---|---|---|
| **A1** | model tier × turns (incl. thinking tokens) | subagent window + billing |
| **A2** | `skills:` preload — full skill body injected at startup | subagent window, per dispatch |
| **A3** | dispatch count — each one a cold prefix | subagent window × N |
| **A4** | agent body bytes | subagent window only |

**Agent bodies are bucket 4. Trimming agent prose saves ZERO main-context tokens.** This is confirmed by the platform, not inferred: `code.claude.com/docs/en/prompt-caching` — *"The parent's cache is unaffected. From the parent's side, the subagent's call and result append to the conversation, leaving the parent's prefix intact."* So the 71,923 B of agent prose costs the main thread nothing, and any proposal framed as "shrink the agent corpus to save tokens" is a false win.

**One narrowing, because "ZERO" is not quite true.** The 14 frontmatter `description:` lines *are* main-thread resident — the same page concedes plugin components "add to the request", and the `sub-agents` field table defines `description` as what tells the parent when to delegate. Agent **bodies** cost the main thread nothing; agent **descriptions** are the only agents/*.md bytes that touch main context, and they are small. Do not rewrite them for cost (and see Appendix B / D1 for why not to rewrite them for recall either).

**Corollary that sets the whole ranking:** the only agent-side axes that move real cost are **A1** and **A3**. A4 is reported for drift risk, never for bytes. A2 has exactly one consumer in the corpus.

**Two documented mechanics that price every dispatch** (`code.claude.com/docs/en/prompt-caching`):
- *"A subagent starts its own conversation with its own system prompt and tool set... Its first request doesn't read the parent's cache, because the two prefixes differ... Subagents use the five-minute TTL even on a subscription."* Two documented exceptions — a `fork` (inherits the parent prefix) and a same-prefix **workflow** fan-out (Claude Code staggers the first agent so the rest read its prefix). Neither reaches claudehut: its seven auditors are distinct agent types with distinct tool lists, so they are genuinely cold.
- Every claudehut agent's window is sized by its **own** model, independent of the parent's (`code.claude.com/docs/en/sub-agents`: *"A subagent's context window is sized by its own model, not the parent's"*), and subagents auto-compact under the same rules as the main conversation. A haiku explorer that reads many files therefore re-summarizes inside its own window rather than failing — an A1 cost, not a ceiling.

**W3 — `sweep` PERMANENTLY DESTROYS committed agent work in a detached-HEAD worktree. [reproduced]**
`wt_branch` (`:40`) returns the literal string `"HEAD"` for a detached worktree; `wt_merged` (`:44`) then runs `git rev-parse "HEAD"` **in the main repo** (no `-C "$w"`), resolving the main tree's own HEAD, so `merge-base --is-ancestor HEAD HEAD` (`:45`) is trivially true and the worktree is classified "merged". `:131` guards `[ "$b" != "HEAD" ]` before deleting the *branch* — **proving the author knew about the detached case** — but `:130` `git worktree remove` runs unconditionally *before* that guard.
*Probe:* detached managed worktree, committed `precious.txt`, clean tree. `status` → `branch=HEAD clean merged`; `sweep` → `removed=1 kept=0`. After: `git branch --contains <sha>` **empty**, `git for-each-ref --contains <sha> | wc -l` → **0**. The commit is unreachable and GC-eligible.
> **Fix:** in `wt_merged`, resolve the tip with `git -C "$w" rev-parse HEAD` rather than `git rev-parse "$b"`; in `sweep`, treat `b == "HEAD"` (or empty) as NOT-merged and keep the worktree with the same `keep (...)` message. ### 2.3 `.lsp.json` — still unvalidated, and unvalidatable on this machine

`command -v jdtls` → NOT_INSTALLED, which is itself why the v0.10 open item never closed. `.lsp.json:2-8` declares `command: "jdtls"` with **no `args`**.

**JDTLS-01 — the standing README question is answered: no `args` are needed.** `README:265` asks maintainers to *"report back if jdtls needs `args` on your setup"*. The upstream `jdtls` Python launcher registers `-data` **with a default** and synthesizes the `-configuration` equivalent itself. From `org.eclipse.jdt.ls.product/scripts/jdtls.py` (read directly): `:83` `cwd_name = os.path.basename(os.getcwd())` · `:99` `jdtls_data_path = os.path.join(cachedir, "jdtls-" + sha1(cwd_name.encode()).hexdigest())` · `:109` `parser.add_argument("-data", default=jdtls_data_path)` · `:123-125` `-Dosgi.sharedConfiguration.area=<config_mac|config_linux|config_win>` + `.readOnly=true` + `cascaded=true`. The `-configuration`/`-data` pair the eclipse.jdt.ls README calls user-provided applies to the raw `java -jar …launcher.jar` form, **not** to the wrapper.
> **Caveat, conditional:** the default is keyed on the sha1 of `basename(getcwd())`, so **two checkouts whose directory basenames match** (`~/work/ewallet` and `~/archive/ewallet`) would share one workspace index — against the server's own *"unique per workspace/project"* requirement. State it as conditional: nothing documents what cwd Claude Code spawns an LSP server with.
> **If per-project isolation is wanted**, the explicit form is `"args": ["-data", "${CLAUDE_PROJECT_DIR}/.claude/claudehut/jdtls-data"]`. **NOT `${workspaceFolder}`** — `plugins-reference` supports exactly three placeholders (`${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_PROJECT_DIR}`); `workspaceFolder` is a sibling config *field*, not a placeholder, and would ship as an unexpanded literal.

**JDTLS-02 — the Java-version floor is a live incompatibility with claudehut's own stated target.** `jdtls.py` `get_java_executable()` (`:22-42`) resolves the JVM from `$JAVA_HOME` first and then `if java_major_version < 21: raise Exception("jdtls requires at least Java 21")`. `README:67` says *"the workflow's standards target Spring Boot 3.x / Java 17+"*. On a machine whose `JAVA_HOME` points at a project JDK 17, `jdtls` throws before the LSP handshake and Claude Code skips the server — the silent-degradation path `README:257` describes for a missing binary, **with a binary that IS on PATH**.
> **Correction that strengthens it:** the Java 21 floor is the **server's**, not the wrapper's — upstream eclipse.jdt.ls README: *"The language server requires a runtime environment of **Java 21** (at a minimum) to run."* That is why `--no-validate-java-version` is **not** a fix: it suppresses a check whose requirement the server still enforces. (`jdtls.py:113` also calls `get_java_major_version()` unconditionally, so even that flag needs a parseable `java -version`.)
> **Fix (README only):** if `java -version` reports < 21, add `"args": ["--java-executable", "/path/to/jdk21/bin/java"]` or `"env": {"JAVA_HOME": "/path/to/jdk21"}` to `.lsp.json`. Both are documented `lspServers` fields.

### 4.3 Serial vs parallel — where the phase-walk is right, and where it is not

**Right:** Discover's two agents, Review's fan-out, and a phase's `[P]` batch are all one-message concurrent (`claudehut-workflow/SKILL.md:102-106`). Reconcile is serial for a real git reason, stated as a design rule at `orchestration.md:44` — *"**Reconcile serialized — never batch-merge.**"*

**Not addressed:** the full test suite runs **once per merged branch** (`bin/claudehut-worktree:112-117`), K times sequentially on the critical path, and then a (K+1)th time in Review. On a Testcontainers-backed Spring suite this is the dominant wall-clock item.
> **Recorded as a wall-clock note, not proposed.** A batch-merge-then-test-once redesign **directly reverses `orchestration.md:44`**, changes zero dispatches (so it is not an A3 finding), weakens a property `evals/worktree-tests.sh:132-134` pins per-reconcile, and would need new replay machinery to restore what `git reset --hard ORIG_HEAD` (`:114`) gets for free today. The (K+1)th run is also **not** repetition: `review/SKILL.md:64` requires fresh evidence on the **final merged tree**, which is a different tree from any intermediate one.

### 4.4 Two mechanics that close off tempting redesigns

**Prefix sharing needs SIX matching fields, and claudehut's fan-out fails on `agent type` — which no config tweak can fix.** `code.claude.com/docs/en/workflows`: *"Two agents that run with the same model, effort level, agent type, tools, output schema, and working directory build the same tools-and-system-prompt prefix…"*. **Correcting a claim that circulated:** it is *not* true that the sonnet reviewers differ on tools — `claudehut-observability-reviewer.md:4-6` and `claudehut-contract-reviewer.md:4-6` are byte-identical on model, effort **and** tools (`Read, Grep, Glob`), and share the cwd. They still cannot share, because their **agent types differ**. **This kills the cheap fix:** normalizing tool lists across the sonnet reviewers buys **zero** cache sharing. Restoring sharing requires collapsing distinct reviewer types into one parameterized type — a design change (§5/F10). And the whole mechanism, plus its `CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS` control, is documented **only** under the dynamic-workflow runtime; whether plain Agent-tool fan-out gets the hold is **[unverified]**.

**`fork` is the only subagent that reuses the parent's cache, and an agent cannot declare it.** `sub-agents`: *"Because a fork's system prompt and tool definitions are identical to the parent, its first request reuses the parent's prompt cache."* No `fork` or `context` field exists in the 16-row agent frontmatter table, so **none of the 14 can become one**. It **is** declarable in SKILL frontmatter (`context: fork` + `agent:`) — but not on `skills/review/SKILL.md`, whose description and Law 7 require it to run inline on the main thread because it owns the `set-review pass` state write. **And make no cost claim for it:** a fork inherits the parent's **model**, which for a distributed plugin is the user's unknown session model, so "cheaper than a cold sonnet auditor" cannot be asserted at authoring time. A1, indeterminate.

**A3 fan-out is already bounded, by the tool allowlists.** All 14 `tools:` lines were checked: **not one contains `Agent` or `Task`**, so no claudehut agent can spawn a subagent at any depth, and `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` is inert for them. This also makes mechanically impossible the "worker spawns its own reviewer" waste that `obra/superpowers` spends five lines of prose forbidding (*"every reviewer a worker spawned duplicated the task review the controller dispatched anyway — a full extra review seat per task"*). **But the property is UNENFORCED:** `evals/conformance.sh:347`'s `BG_OK` list **includes `Agent`**, so an auditor that declared it would stay green. If this is meant to be an invariant it needs its own assertion. *(`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, default 20, governs the main thread's calls and is simply not binding at a 6-way fan-out; lowering it would bound A3 by producing errors, not savings.)*

**One conditional pressure worth naming:** `agent-sdk/subagents` — *"Claude Opus 5 delegates to subagents more readily than earlier models"*, and the `claude_code` preset adds a system-prompt line telling Opus 5 not to call the Agent tool unless asked. This applies **only on Opus 5 sessions**; nothing in claudehut pins the main-thread model. Whether claudehut's explicit dispatch tables read as "asked to" is inference the docs do not settle, and cannot be settled empirically today. **[unverified]**

## 7. What could not be measured

**No dispatch-frequency claim in this document is empirical.** Two structural reasons, both in the repo:

1. **13 of 15 installs run stale cached plugin code.** All 15 `claudehut@claudehut` installs are project-scoped with the version pinned at install time and no auto-update (`.claude/reviews/v0.11-tracking.md:481-482,:487-498`); only two are on 0.10.0 — the rest run 0.9.1 ×7, 0.9.0, 0.8.0 ×2, 0.6.0, 0.5.1, 0.2.0. Each runs **its own cached copy** of `scripts/bootstrap.sh` and `hooks/hooks.json`. *(Distinct from §3's 15/15 project-scope figure — same population, different property.)*
2. **The ledger is written to a directory `claudehut-init` gitignores.** `scripts/record-dispatch.sh:17` states it: *".claude/claudehut/state/<sid>.dispatches.jsonl (ephemeral; claudehut-init gitignores state/)"*. Only **2 files across all repos** match `*.dispatches.jsonl`. The instrumentation exists and is wired (`hooks/hooks.json:34,:72,:86`) — **do not propose adding dispatch hooks**; the gap is persistence, which is F5.

**The one command that produces real data today, with zero setup:**

```
/usage        # then press d / w to toggle 24h vs 7d
```

`code.claude.com/docs/en/costs`, Attribution block: *"recent usage attributed to skills, subagents, plugins, and individual MCP servers, each shown as a percentage of the total"*, plus Behavior flags for long context and cache misses *"flagged when one accounts for 10% or more of recent usage."* Available on Pro/Max/Team/Enterprise, computed from local session history, **no collector, and unaffected by D8** because it is a native Claude Code surface rather than plugin code. `README.md` mentions it zero times (`grep -in usage README.md` → exit 1) — the cheapest documentation win in this plan.
- **[unverified]:** whether Attribution renders claudehut's own agent/skill names verbatim or redacts them the way the OTEL counters do. Worth one empirical check before F7 promises granularity.
- **Do not infer fan-out from the cache-miss flag** — the same page defines that mechanism as a **time gap**: *"your first message after a break longer than the cache lifetime misses the cache."*

**Everything else needs setup that does not exist yet.** OTEL grouping on `query_source × model × effort` (F7) is the right query, but `grep -rn CLAUDE_CODE_ENABLE_TELEMETRY` over `bin/`, `README.md` and `evals/conformance.sh` returns **nothing** — claudehut never enables telemetry, and `bin/claudehut-init:385` deliberately leaves the exporter endpoint and headers in the user's own environment. So a user must enable telemetry **and** run a collector before a single row exists. Combined with D8, there is **no evidence any install is emitting these metrics today.**
